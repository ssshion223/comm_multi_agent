# 路由智能体

`route_agent` 根据网络拓扑、链路剩余带宽和测试业务需求，搜索候选路径、联合分配资源，并将被接纳业务的路径提交到仿真环境。

本目录是供主程序调用的 Python 包，没有独立运行入口。主程序负责初始化运维数据，再启动一轮路由计算与提交。每轮处理一个网络状态快照，不会自动监听事件或持续重规划。

## 模块职责

| 文件 | 核心内容 | 职责 |
| --- | --- | --- |
| `body.py` | `RouteAgent` | 统一入口，组织组件并管理客户端生命周期 |
| `ops_input_adapter.py` | `OpsInputAdapter` | 复制运维数据、转换业务请求、处理链路剩余带宽 |
| `path_finder.py` | `PathFinder` | 根据簇结构和 QoS 需求生成候选路径 |
| `route_planner.py` | `RoutePlanner` | 联合规划业务路径，组织规划后的仿真提交 |
| `data_class.py` | 路由数据类及校验函数 | 定义请求、候选路径和规划结果 |
| `__init__.py` | 包级导出 | 集中导出可供主程序导入的类 |

本包依赖同级 `ops_agent` 中的网络数据结构，以及 `http_utility` 中的 `SimClient`。仿真地址、令牌和调用方标识由工程的 `config` 配置提供。路由计算不调用大模型，也不要求启动 A2A 服务。

## 主程序调用逻辑

主程序先完成运维智能体初始化，确保拓扑、簇图、业务集合和剩余带宽对应同一轮网络状态，再创建或复用 `RouteAgent`，调用 `start(ops)`。

`start(ops)` 按以下顺序执行：

1. 调用 `OpsInputAdapter.prepare(ops)`，建立独立的路由计算快照。
2. 创建 `PathFinder` 和 `RoutePlanner`。
3. 对每项测试业务调用 `PathFinder.compute()`，收集整批候选路径。
4. 调用 `RoutePlanner.run()`，完成全部业务的联合规划。
5. 规划完成后，逐条提交被接纳的业务路径。
6. 全部提交成功后，返回 `PlanningResult`。

因此，`RouteAgent.start()` 会发送真实仿真请求；候选搜索和整批规划完成前不会下发路径。主程序不需要再手动提交同一轮结果。

如果只需计算，调用方可以分别组织输入适配、候选搜索和 `RoutePlanner.plan()`。`plan()` 只返回规划结果，不发送请求；`run()` 则在规划完成后继续提交。

使用结束后，主程序调用 `RouteAgent.close()`。由 Agent 创建的客户端由它关闭；通过构造参数传入的客户端仍由调用方管理。运维智能体的关闭也由主程序负责。

## 运维输入与数据转换

`OpsInputAdapter.prepare()` 读取以下属性：

| 运维属性 | 内容 |
| --- | --- |
| `ops.topology_manager.topology` | 全网节点和链路 |
| `ops.topology_manager.cluster_graph` | 簇成员、网关、簇内连接和簇间连接 |
| `ops.link_budget_analyzer.services` | 背景业务与测试业务 |
| `ops.link_budget_analyzer.residual_bw` | 每条链路在本轮规划前的剩余带宽，单位 bit/s |

适配器将这些数据一起深拷贝，在副本中用剩余带宽替换链路带宽，仅将 `category == "test"` 的业务转为 `ServiceRequest`。运维业务的 `requirement` 对应路由请求的 `qos`。

背景业务占用已经由运维模块计入剩余带宽，路由模块不会再次扣除。适配器不修改上游对象、不刷新文件，也不发送网络请求。主程序应保证复制期间输入状态一致。

缺少拓扑、簇图或任意链路的剩余带宽时，适配器抛出异常。`normalize_link_qos()` 将有限负剩余带宽视为零容量，拒绝 NaN、无穷和其他非法 QoS 参数。业务需求仍须满足非负要求。

## 候选路径搜索

`PathFinder.compute(service)` 针对单项业务生成满足约束的简单路径，不负责多业务资源分配。

同簇业务通过簇内链路搜索；跨簇业务按“源节点到源簇网关、骨干网到目的簇网关、目的簇网关到目的节点”分阶段搜索。默认骨干链路类型为 `fiber` 和 `satcom`，可在创建搜索器时调整。节点属于多个簇时，会尝试不同的端点所属簇组合。

搜索过程中跳过离线节点、断开链路和已访问节点。每扩展一跳就累计 QoS，不满足业务要求的分支立即停止。端点不存在时抛出异常；端点离线或没有可行路径时，返回空候选列表。

| 指标 | 路径累计方式 |
| --- | --- |
| 时延 | 各跳时延求和 |
| 抖动 | 按不相关波动假设，将各跳抖动平方求和后开根号 |
| 带宽 | 取沿途链路剩余带宽的最小值 |
| 误码率、丢包率 | 按“已有累计值 + (1 - 已有累计值) × 当前链路值”组合 |

候选路径保存节点序列、链路序列、累计 QoS、QoS 余量评分和资源成本。资源成本为业务需求带宽乘以路径跳数；评分按各指标的归一化余量加权计算。候选结果按评分降序、成本升序及链路序列排序，并按链路序列去重。

搜索器会缓存簇内和骨干连接关系，调用方不应在复用搜索器期间修改这些结构。拓扑变化后应重新建立计算快照和搜索器。

## 联合规划与求解策略

`RoutePlanner.plan(candidates)` 先检查业务 ID、优先级及候选路径合法性，再联合选择业务和路径。每项业务最多选择一条路径，所有被接纳业务在每条链路上的带宽需求总和不得超过该链路剩余容量。

规划目标按以下顺序比较：

1. 最大化被接纳业务的优先级总和。
2. 总优先级相同时，最小化总资源成本。
3. 前两项相同时，最大化总 QoS 评分。

业务接纳不是简单地按优先级依次占用资源，多项业务可能通过组合或换路得到更好的整体结果。

当前规划器根据输入自动选择策略：

- 如果所有可能使用同一链路的业务一起接纳也不会超载，各业务独立选择，得到候选集合内的最优结果。
- 存在资源竞争时，先通过多种业务顺序和路径顺序生成可行解。
- 当估算的组合搜索工作量不大于局部改进工作量时，执行带优先级上界剪枝的精确搜索。
- 其他情况下执行局部改进，包括重新选路、移除一项业务后重新填充，以及两项业务替换一项业务。

精确分支的最优性限定在提供的候选集合内。局部改进分支通常只保证可行性，不统一保证全局最优；结果中的 `solver_info` 记录所选策略、目标值、优先级上界及最优性标记，调用方应据此判断求解结论。

## 结果及状态读取

| 数据类 | 内容 |
| --- | --- |
| `ServiceRequest` | 业务 ID、源节点、目的节点、QoS 需求和优先级 |
| `CandidatePath` | 有序节点和链路、累计 QoS、评分、资源成本 |
| `CandidateResult` | 一项业务及其候选路径列表 |
| `PlanningResult` | 接纳结果、未接纳原因、链路新增占用和求解信息 |

`PlanningResult` 的主要字段为：

| 字段 | 含义 |
| --- | --- |
| `accepted` | 业务 ID 到所选路径的映射 |
| `rejected` | 业务 ID 到未接纳原因的映射 |
| `link_load_bps` | 本轮新增的链路带宽占用，不包含已有背景负载 |
| `solver_info` | 求解策略、状态和最优性信息 |

没有可行候选路径的业务标记为 `no_qos_feasible_path`；有候选但未被规划器接纳的业务标记为 `resource_conflict`。`to_service_results()` 可将接纳路径转换为运维数据结构中的 `ServiceResult` 列表。

`RouteAgent` 保存本轮的 `services`、`path_finder`、`route_planner` 和成功返回后的 `result`。`RoutePlanner.run()` 另外保存 `result`、成功提交的 `receipts` 和提交使用的 `request_ids`。直接调用 `plan()` 时应读取其返回值，它不会更新这些运行状态。

## 路径提交与异常处理

提交逻辑位于 `route_planner.py`。`run()` 负责整批规划后的顺序提交，`submit()` 负责单项业务的报文构造和回执检查，实际 HTTP 请求复用 `SimClient.post_json()`。

请求发送到 `/services/{serviceId}/path`，由客户端基础地址补齐 `/api/open/v1` 前缀。请求体包含 `requestId`、`srcNodeId`、`dstNodeId` 和 `segments`；每个段的类型为 `link`，段 ID 按选中路径的链路顺序排列。客户端负责携带配置中的令牌和 Agent 标识。

只有响应同时满足 `code == 0` 和 `data.result == "accepted"` 才视为成功。HTTP 错误或业务拒绝会抛出异常，停止后续提交；已经成功的提交不会回滚。计算完成不代表全部路径已经下发成功，应结合 `receipts` 判断实际提交进度。

如果 `start()` 在提交过程中失败，Agent 的 `result` 尚未赋值，但其 `route_planner.result` 保留完整计算结果，`route_planner.receipts` 保留此前成功的回执，`route_planner.request_ids` 保留已经尝试提交的请求标识。

单条提交允许传入请求 ID；不传时生成新 ID。对同一次提交进行显式重试时，应复用原请求 ID。当前没有自动重试和事务式批量提交，直接调用 `submit()` 返回回执，但不会自动将其写入 `receipts`。

## 运行边界

规划使用本轮快照，不直接扣减输入容量，也不在多轮调用之间自动预留资源。重复运行前，主程序需要准备与实际占用一致的新状态；重新执行整轮流程会重新生成提交请求 ID。

同一链路 ID 对应共享容量池，两个方向的业务共同占用该容量。簇成员和邻接关系由上游提供，本包不会创建新物理连接或自行修改簇归属。

候选搜索可能随网络规模快速增长，规划器的自适应策略不等于对整个流程提供固定耗时保证。当前没有后台事件循环、自动故障恢复或持续重规划；输入与仿真场景的一致性由主程序及运维模块负责。
